# Phase 6: Opt-in delivery

## QR and share links (menu 3)

1. Pick a built-in template or a saved Studio preset and choose **Create invitation**. It starts a recipient-only loopback listener if one is not running. A loopback link only works on the creator's device.
2. For another device, first choose a private IPv4 interface and press **Start LAN (HTTP)**. If loopback is already running, stop it first; stopping invalidates the old links. The header shows the interface name and actual IP and port.
3. Highlight the invitation in the control center. **Copy link** uses the terminal clipboard (OSC 52). If your terminal doesn't support it, copy the visible URL manually. **Show QR** displays a high-contrast, URL-only code with a quiet zone. A Unicode terminal and roughly 45 columns × 24 rows are needed to show the whole code.
4. Send the link or show the QR only to a willing recipient. The invitation expires after **2 minutes**. Opening it shows the template, title, duration bound, audio disclosure and expiration. **Decline** discards the invitation. **Accept** opens a separate consent screen; only **Launch Simulation** begins the simulation.
5. **Revoke selected** cancels a pending invitation or terminates its accepted session, even while running. A scan or link copy is not evidence of delivery.

## Wi-Fi Device Discovery & Multi-Device Invitation (menu 4)

1. Select the interface for your trusted LAN and press **Start LAN (HTTP)**. Wired LAN also works when clients can reach that interface. **Open joining** creates a separate, five-minute enrollment link. Copy it and give it to willing recipients on the selected subnet. **Close joining** invalidates this entry link; it does not disconnect browsers that already opted in.
2. Recipients open the link and choose **Advertise availability**. An optional display name is self-reported, not verified. No physical device type or Wi-Fi association is inferred. Keep the tab visible; **Stop availability**, Exit, or Escape stops the advertisement. Closing or hiding the tab also causes the advertisement to lapse if it can't renew.
3. Use **Space** for individual selection, **Select all** for eligible browsers, **Deselect all**, or **Clear unavailable**. A browser with a pending invitation or a live accepted session is busy. The list shows availability, invitation status, and the last check-in. The control center shows selected and discovered counts, invitation outcomes, and active simulations.
4. Choose a template or saved Studio preset and press **Queue for selected**. An invitation goes into each selected browser's own inbox; there is no push, notification permission or automatic navigation to a simulation. A failed queue does not affect a successful queue to another device. **Pending (unconfirmed)** means there is no verified response; it does not mean a person has seen the invitation. **Failed** means the browser's availability ended before responding, or a new request could not be queued (the send panel explains why). Each recipient accepts or declines independently. **Revoke selected** also works on individual active sessions.
5. **Back** returns to the main menu without closing the service. **Stop listener** or exiting POPTRAP terminates all delivery sessions and discards links, leases and status history. It does not stop the separate Create Prank/Studio experience server.

Discovery uses a **browser rendezvous**, not a Wi-Fi scan, device inventory, multicast protocol, or router client list. Same Wi-Fi alone is insufficient. There are no outgoing connections to discovered devices: their already-open browsers poll their own inboxes. Client isolation on guest Wi-Fi, host firewalls, VPNs and different subnets can prevent connectivity. If the OS cannot enumerate an eligible local interface, LAN controls remain unavailable and menu 3 can still create loopback links.

## Local rendezvous protocol (`/delivery/v1`)

One `DeliveryServer` binds the literal IPv4 address shown in the terminal and chooses an ephemeral TCP port. It accepts direct peers on loopback or the selected RFC 1918/link-local subnet. The `Host` must equal the listener's exact address and port. JSON requests require the matching `Origin`; cross-origin access, preflight grants, and proxy-supplied peer identities are not supported. There are no cookies. All API calls use `POST` with a JSON object of the indicated shape. Protected operations use `Authorization: Bearer <capability>`. Since [Phase 9](phase-9.md), `consent` and subsequent playback commands also use `X-Poptrap-Document`, a cryptographically random 32-byte key encoded as 64 lowercase hex characters. The player generates it once for the document and keeps it outside URLs and browser storage.

| Command under `/delivery/v1/` | Body | Scope and effect |
|---|---|---|
| `invite` | `{ "token": "…" }` | Read a pending share invitation; no session data or state change |
| `announce` | `{ "token": "…", "name": "…", "available": true }` | Use the creator's enrollment link to obtain an in-memory browser lease |
| `inbox` | `{}` | Renew the lease and return only that browser's pending invitation, if any |
| `withdraw` | `{}` | Stop advertising using the lease; does not end an already accepted simulation |
| `respond` | `{ "token": "…", "decision": "accept" }` or `"decline"` | A device invite additionally requires the matching live lease. Either decision consumes the invitation; only Accept returns the one-session grant |
| `session` | `{}` | Read review state with the play grant; active payload and private playback text also require the launching document’s key |
| `consent` | `{ "consent": true }` | Launch the accepted session once, binding it to this document; only JSON `true` is accepted |
| `exit`, `complete` | `{}` | End only the granted session; an active session also requires its document key |

The delivery pages are `/invite`, LAN-only `/availability`, and an inert `/play` shell. Phase 7 adds a recipient-only `/scan` helper for images, pasted links and on-device diagnostics; see the [mobile guide](phase-7.md). All pages use a fixed set of packaged assets. The share and enrollment capabilities are URL fragments, not query strings or API paths. The browser clears the fragment immediately and keeps the capability in memory. Reloading the page loses it: reopen the original link if it's still valid and pending, or ask for a new invitation. The QR contains exactly the invitation URL and its short-lived invitation token, not a session identifier, play grant, recipient data or executable content.

Confirming an invitation and pressing Launch are separate actions. The dedicated `PrankController` reuses the ordinary session store, scheduler, Studio compiler, and consent/exit/reveal rendering, but has no shared session IDs or storage with the localhost administration app. Internal IDs are not sent to recipients. The existing Bluetooth module continues to use its own capability checks and invitation transport and does not make these HTTP links reachable via Bluetooth.

## Safety, bounds, and deployment limits

- Capabilities come from 32 bytes of system randomness and are checked in canonical base64url form. The manager serializes decisions and binds scopes separately. Expiry uses monotonic time; accepted, declined, expired, failed and revoked invitation tokens are never accepted again.
- Browser leases renew every four seconds while the availability tab is visible, expire after 20 seconds without renewal and cannot renew beyond 10 minutes. An accepted session has 45 seconds to launch before the grant expires. Active simulation duration follows the existing hard maximum of 180 seconds, with only a brief read-only reveal after ending. Foreground tabs check for revocation approximately every 1.4 seconds; a lost connection stops the local effect when detected. Exit and Escape stop local effects immediately. Closing the page attempts cleanup; time limits remain in effect if the close request never reaches the host.
- Defaults allow at most 8 pre-consent/running delivery sessions, 32 availability records and 64 recent invitation records per listener. Ended statuses and unavailable records are discarded after three minutes or at shutdown. JSON bodies are limited to 1 KiB, with request deadlines, per-peer and global rate limits, and stricter enrollment limits. Peers are counted only in short in-memory rate-limit windows. No recipient analytics, persistence, fingerprints or access logs are kept by the delivery service.
- No session creation, presets, config, Studio, health data, logs, directory browsing, arbitrary file paths, outbound URL fetches or WebSockets are exposed on the delivery port. Creator commands stay on the terminal and the separate loopback-only Control Center. The content policy denies framing and external resources; capabilities are never passed through client-controlled redirects. The SIMULATION badge stays visible; no templates can execute code supplied by a recipient or affect browser tabs, files, accounts or device settings.
- **LAN HTTP is not encrypted.** People on the network who can observe or alter traffic could copy capabilities or tamper with responses. A token authorizes its bearer, not an authenticated person. Use only on a trusted private LAN and share links selectively. This is not a public deployment. Do not tunnel, port-forward, or publish the listener. A future public delivery design would need HTTPS, a new threat model, and separate operational controls; it is unsupported here.

## Verification and Phase 7 handoff

Automated coverage includes canonical QR payloads, token generation and concurrency, both expiry windows, replay/revocation, request and subnet validation, TCP binding and isolation, opt-in selection, partial queue failures, accept/decline, and multi-session cleanup. Node tests use a simulated DOM and fetch; Textual's LAN controls use an injected interface. Separate smoke tests used the Linux sandbox's own interface and headless Chromium with two tabs. The generated QR matrix was also decoded with an independent software QR decoder, not a physical camera. None of this verifies a physical phone, Wi-Fi radio, camera scanner, or Bluetooth adapter. The full TUI suite used Textual 8.2.8, and the Phase 6 terminal tests also passed on 1.0.0. Pinning the repository’s existing declared minimum (0.85) does not work because the pre-existing theme module requires `textual.theme`.

For hardware sign-off, try a physical creator host and two phones/laptops on a trusted Wi-Fi network. Scan a terminal QR with a phone camera, confirm the preview never starts the simulation, and test replay and expiration. Join both devices separately, queue for both, decline one and launch on the other. Revoke the running session, test Exit and Escape, let a device go offline, and stop the listener. Record the tested OS/browser/terminal/router conditions; repeat on the supported OS matrix before treating the browser workflow as hardware-verified.

The scoped recipient protocol also serves the browser-first [Phase 7 mobile workflow](phase-7.md). Physical-device and browser matrix sign-off is separate from these local tests. No native app, cross-internet transport, or automatic device discovery ships here.
